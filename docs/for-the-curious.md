# For the curious: how the checking works

[The README](../README.md) says everything you need to use LOKF Registrar. What follows is the reasoning behind it, for anyone who wants to know what is actually being checked and why.

## What LOKF adds over plain OKF

[OKF](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md), in plain terms, is a folder of Markdown files, one idea per file, each starting with a small YAML block whose only real requirement is a `type` (`Service`, `Policy`, `GlossaryTerm`, and so on).

[LOKF](https://lokf.nolan-nichols.com/specification/) is that same folder, held to a stricter, more precise dialect: every field and relationship is bound to a public vocabulary (schema.org / DCAT / PROV-O), so the bundle can be losslessly turned into a knowledge graph and queried like a database. That precision is what this plugin checks for:

- A **bundle-root semantic header** on the root `index.md` - `lokf_version`, `base_iri`, `context`, `title`, `description`, `license`, `publisher` - the keys that lift the whole bundle into a graph.
- **`base_iri` authority and format checks** - it must be a syntactically valid absolute IRI, terminated with `/` or `#` (so an id is just the two joined together), and in a namespace the project actually owns (not, say, `https://github.com/<org>/<repo>/knowledge/...`). It is an *identifier namespace, not a hyperlink*: a concept's `id` only looks like a URL, so it need not resolve - a 404 is valid by design, though a [Cool URI](https://www.w3.org/Provider/Style/URI) that could double as a working link later is the ideal. The check is on form and authority, never on whether the address is live.
- A **controlled type vocabulary**, derived from the LOKF schema (`Dataset`, `Table`, `Metric`, `Service`, `Playbook`, `Tutorial`, `Explanation`, `Policy`, `GlossaryTerm`, `Reference`, `Document`, `Role`, `AttestedComputation`, `Person`, `Organization`) with type-specific fields - e.g. `Table`/`Dataset` need structured `fields`/`distribution` objects, never bare strings or URLs. The list is a starting point, not a ceiling: a bundle that extends LOKF with its own domain schema (LinkML, importing LOKF's, validated with `lokf validate --schema`) adds that schema's classes under *Settings → Type vocabulary*. The field checks key on the exact class name, so a domain subclass of `Metric` is not held to its parent's recommended fields.
- The optional Diátaxis **`genre`** facet (`tutorial` / `how-to` / `reference` / `explanation`).
- **Typed relationships** in place of bare links - the schema's full `RelationType` set (`isPartOf`, `hasPart`, `references`, `dependsOn`, `derivedFrom`, `about`, `sameAs`, `relatedTo`, `wasAttributedTo`, `definedBy`, `measures`, `joinsWith`, `source`, `memberOf`, `holder`), plus a generic `relations` list - each with a precise meaning, and checked to make sure the note it points at actually exists.
- **`id` consistency** - does a concept's `id` match what its `base_iri` and file path would produce?
- **Trust/lifecycle field shapes (OKF v0.2 §5)** - when a bundle uses them, that `verified`/`generated` events are well-formed `{ by, at }` with an OKF §7 actor (`human:<id>`, `process:<id>`, or `<producer>/<version>`), `status` is one of the schema's lifecycle values, `stale_after` is a datetime or a bare date, and each `sources` entry names its `resource`. These fields originate in OKF but are defined in the LOKF schema and are the substrate LOKF's curation ceremony stands on, so their *shape* is checked here (never their credibility *depth* or trust-tier display) - and the two fields OKF marks REQUIRED, a `generated.by` actor and each source's `resource`, are errors, as is a value the schema's own patterns reject since lokf 0.8.0 (a malformed actor, `sources[].author` or `email`, or an `http_method` outside its enum); the rest are warnings.

## The OKF v0.2 base layer

Because every LOKF field is a LOKF schema slot, the plugin already has what it needs to check the plain OKF rules *underneath* the LOKF dialect - so it does, rather than leaning on a separate tool that might not be installed or kept up to date. The spec is the authority: a rule exists here because OKF v0.2 (or the LOKF schema that mirrors it) says so. These are the `okf/*` findings, switchable off in one place (*Settings → OKF v0.2 base layer*) if you do run a dedicated OKF validator. **Severity follows the spec's own force:** what OKF marks *REQUIRED / MUST* (or lists under §11 conformance) is an **error**; the shape of optional fields and the migration hints are warnings. Those mandatory errors can be **temporarily downgraded to warnings** with *Enforce OKF conformance as errors* (a not-recommended break-glass toggle in the same settings group) - for a mid-migration bundle, keeping the findings visible without blocking.

- **A required `type`** (OKF §4.1/§11, REQUIRED) - **error.** The one always-required OKF key, and `required` in the LOKF schema too. Flagged only when the note is plainly a concept (it carries other LOKF fields), so an ordinary vault note with just tags or aliases is still left alone.
- **The `Attested Computation` contract shape** (§10) - a missing `runtime` is an **error** (§10.2 REQUIRED, and `required` in the schema); the shape of the optional `parameters` / `executor` / `attester` / `computation` fields, and the expectation of a body `# Computation` block, are warnings.
- **Reserved `index.md` / `log.md` structure** (§8/§9, §11 conformance) - **errors.** A non-root `index.md` carries no frontmatter (only a bundle-root one may, and only `okf_version`), and `log.md` date headings MUST be ISO 8601 `YYYY-MM-DD`.
- **v0.1 → v0.2 migration hints** (§13) - warnings. A legacy `timestamp` (superseded by `generated`) and a body `# Citations` list (superseded by `sources`); v0.2 consumers still tolerate the v0.1 forms, so these only nudge.

## What this plugin deliberately does *not* check

What stays out of scope is the *verdict*, not the paperwork. For the §5 trust/lifecycle fields the plugin checks their *shape* but never their credibility *depth* - it won't weigh a source's signals, rank trust tiers, or decide whether a claim is current. Nor does it execute anything: an `Attested Computation`'s contract is checked, but running the computation, inspecting a receipt, and returning an attestation verdict (§10.5) are runtime concerns a consumer performs, not an in-editor linter's.

## Where this fits: the "Schema-valid" tier

The companion [lokf-agent-skills](https://github.com/noelmcloughlin/lokf-agent-skills) project describes four levels of trust a claim in a bundle can earn: **schema-valid** (the frontmatter is well-formed and its relations resolve), **source-consistent** (an agent re-checked it against its source), **human-confirmed** (a named person vouches for it), and **proven-in-use** (a real question got answered from it). Each proves less than its name suggests. This plugin checks the first tier as you write, inside the editor. It cannot tell you whether a claim is *true*; that takes a librarian pass and a curator's review, and [LOKF Curator](https://github.com/noelmcloughlin/obsidian-lokf-curator) is where the latter happens in the editor.

There is no dependency in any direction. This plugin reads Markdown and YAML and works on any LOKF bundle however it was produced - by hand, by the `lokf` CLI, or by the skills - and never loads or calls into a skill, an agent, or another plugin; the skills, in turn, rely on `lokf validate`, not on this plugin. LOKF Curator sits one tier above, equally independent - neither plugin detects whether the other is installed.

## Where the bundle lives, host by host

The plugin sees a vault; where that vault's folder sits in the wider world is the sidecar's business - but it decides what a review can reach and what syncs. The skills lay down one layout everywhere: `.lokf/knowledge/` is the real folder, and `knowledge_bundle` beside it is a link (a junction on Windows) so folder pickers, which hide dot-folders, have a name to open.

- **A code repository.** The librarian derives the bundle from code and docs; you check it in `knowledge_bundle` opened as a vault. Concepts cite sources that sit *above* that small vault - `src/…`, `docs/…` - so no plugin can open them from there; LOKF Curator shows such a source as a path to copy rather than pretending to have checked it.
- **Your vault, kept in git.** Run the skills at the host and the sidecar lands beside your notes. `.lokf/` is a dot-folder your vault never indexes, and the doorway link resolves inside the vault, so Obsidian skips that too: your main vault never sees the bundle, and you curate in a second vault opened through the doorway. One repository, not two - the bundle travels with the notes it was distilled from, and splitting it into a repository of its own is a later choice for a team, never a starting one.
- **A shared drive or a SharePoint library.** The sidecar is just files and syncs as such (Microsoft's list of restricted OneDrive and SharePoint names has nothing against a leading dot), but OneDrive syncs neither symbolic links nor junctions, so the doorway is per machine (`just lokf-link` in `.lokf/`) or the bundle is opened by path. A team that wants a synced, visible folder may rearrange by hand - a real `knowledge_bundle/` with `.lokf/knowledge` linking onto it; the skills' `portability.md` says how - and this plugin then detects the folder as a bundle inside a vault (README, *Which folder is the bundle*), with the same cost if the shared folder is also a vault.
- **Many hosts, one vault.** Obsidian follows a link whose target lies *outside* the vault. Link each repository's `.lokf/knowledge` into a folder of your own vault (`projects/acme-knowledge → ~/git/acme/.lokf/knowledge`) and list those folders under *Bundle root folders*: every bundle you curate, in one vault, beside the notes you keep about them - and the sources now sit inside the vault, so LOKF Curator can open them beside the claim. This is the one arrangement that puts exhibits in your vault's index, with the cost the README names; keep such links out of Obsidian Sync, which does not carry them.

What Obsidian 1.13.7's file reconciler does with a link on each host is recorded in the skills' own playbook, [Open the knowledge bundle in Obsidian](https://github.com/noelmcloughlin/lokf-agent-skills/blob/main/.lokf/knowledge/playbooks/open-bundle-in-obsidian.md).

## Philosophy: warnings, not errors, almost everywhere

LOKF's own rules stay permissive by design: missing optional fields, an unknown `type`, and broken cross-links must never cause rejection. This plugin reserves **errors** for genuinely structural problems - a `base_iri` that isn't a syntactically valid IRI, doesn't end in `/` or `#`, or lives in a namespace the project doesn't own; a `Field`/`Distribution` given as a bare string instead of a structured object; a value the LOKF schema's patterns reject (an actor, `sources[].author` or `email` in the wrong shape, an `http_method` outside its enum), since `lokf validate` fails on it; and the OKF v0.2 rules the *authoritative* spec itself marks REQUIRED or MUST - a concept with no `type`, an `Attested Computation` with no `runtime`, a non-root `index.md` that carries frontmatter, a `log.md` date heading that isn't ISO 8601, a `generated` block with no `by` actor, or a `sources` entry with no `resource`. Those OKF ones are errors because the spec (and the LOKF schema that mirrors it) says the field or structure is required, not by this plugin's preference; where OKF says a field is optional or merely superseded, it stays a warning - and, as a not-recommended break-glass measure, they can be **temporarily downgraded to warnings** (mid-migration, say) via *Settings → OKF v0.2 base layer → Enforce OKF conformance as errors*, without losing the finding. Everything else - an unrecognized type, a missing recommended field, an unresolved relative link, an `id` that doesn't match what its path and `base_iri` would give it - is a warning you can act on or ignore.

Everything this plugin writes, it writes on an explicit command and to the *form* of a record, never to a claim: a header template, a mechanical fix, a wikilink block projecting relations you already declared, a map built from genres you already set. Auto-fix is offered only where the correction is mechanical and unambiguous. The **Fix safe issues in the active note** command appends a missing `base_iri` terminator (`/`), rewrites a known type alias to its canonical class (`runbook` → `Playbook`), and turns a bare-string relation into a one-item list - each a format-preserving edit, in one undo step. It never guesses a value the project owns: it will not pick a `base_iri`, move one into a namespace you control, or invent a publisher identity - those stay human decisions, flagged but not touched.
